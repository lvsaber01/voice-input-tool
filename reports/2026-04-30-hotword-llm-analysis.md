> 📅 2026-04-30 | Saber 分析

> 聚焦：**热词系统** 与 **LLM 后处理** 两个功能

## 一、功能定义与需求分析

### 1.1 热词系统（Hotword System）

**是什么**：允许用户自定义词汇表，在 STT 识别过程中或识别后，强制将识别结果中的易混淆词替换为正确词。

**典型场景**：
- 人名/地名："刘洋"被识别为"刘洋"，"鹤壁"被识别为"贺壁"
- 专业术语："CUDA"被识别为"库达"，"Kubernetes"被识别为"库伯奈提斯"
- 公司/品牌名："字节跳动"被识别为"字节跳动"
- 英文混排："iPhone"被识别为"爱凤"，"Vue.js"被识别为"V js"
- 方言口音：南方的"四/十"不分、"刘/牛"混同

**本质问题**：STT 模型基于通用语料训练，对长尾词汇识别率低。热词系统是对模型识别能力的定向增强。

### 1.2 LLM 后处理（LLM Post-Processing）

**是什么**：STT 识别出原始文本后，调用 LLM 进行二次加工（润色、纠错、排版），输出更高质量的最终文本。

**典型场景**：
- 口语纠错："呃...那个...我觉得吧这个方案不太行" → "我认为这个方案不太可行"
- 标点补全：STT 不输出标点 → LLM 补上正确的逗号、句号
- 格式化：会议纪要自动分段、加要点编号
- 中英混排：自动修正大小写、空格
- 翻译：中文语音 → 英文文本输出
- 风格转换：口语 → 书面语、随意的 → 正式的

**本质问题**：STT 只做"语音→文字"的映射，不理解语义和上下文。LLM 后处理是对输出质量的语义级提升。

## 三、对现有架构的影响

### 3.1 热词系统 — 架构侵入性分析

**影响极小**。热词系统是一个纯文本后处理步骤，插入位置明确：

```
当前流程：
STT 输出 raw_text → command.py 匹配 → injector 注入

加入热词后：
STT 输出 raw_text → [热词替换] → command.py 匹配 → [LLM 后处理] → injector 注入
```

**需要新增的组件**：
- `core/hotword.py` — 热词替换引擎（~100-150 行）
- `config.py` 新增 `HotwordConfig` — 热词配置数据类（~30 行）
- `config.yaml` 新增 `hotword:` 配置节
- Web 配置页面新增热词管理 UI
- `hotwords.txt` — 用户热词表文件

**不需要修改的核心模块**：
- `engine.py` — 只需在 `_on_stt_complete_inner` 和 `_on_realtime_segment` 中加一行调用
- `stt_*.py` — 无需修改（后处理模式）
- `platform_adapter/` — 完全无关

**可选拓展**（FunASR 原生热词）：
- FunASR Paraformer 支持 `hotword` 参数，在推理时注入热词，影响模型解码过程
- 这是"模型级"热词，比"文本替换级"效果更好，但仅限 FunASR 引擎
- 双层热词 = 原生 + 文本替换，覆盖所有引擎

### 3.2 LLM 后处理 — 架构侵入性分析

**影响中等**。需要新增 LLM 调用模块和异步处理链路：

**需要新增的组件**：
- `core/llm_postprocessor.py` — LLM 后处理引擎（~200-300 行）
- `config.py` 新增 `LLMConfig` — LLM 配置数据类（~50 行）
- `config.yaml` 新增 `llm:` 配置节
- Web 配置页面新增 LLM 设置 UI
- `prompts/` 目录 — 预设 prompt 模板

**需要修改的核心模块**：
- `engine.py` — `_on_stt_complete_inner` 中注入后处理步骤（INJECTING 前多一步）
- `_on_realtime_segment` — 实时模式下后处理延迟影响体验（需异步流水线）

**关键设计决策**：
1. **同步 vs 异步**：LLM 调用耗时 1-5 秒，必须异步
2. **实时模式适配**：实时转写段落间隔 0.8s，LLM 后处理会破坏实时性
   - 方案 A：实时模式跳过后处理（仅批量模式生效）
   - 方案 B：LLM 流水线（STT 段 N 转写时，LLM 同时处理段 N-1）
   - 推荐：**方案 A 先行**，简单可靠
3. **LLM 后端选择**：支持多种后端，用户按需配置
   - 本地：ollama、vllm、llama.cpp
   - 云端：OpenAI、DeepSeek、通义千问
   - 统一 OpenAI 兼容 API 格式

### 3.3 处理链路全景（加入两个功能后）

```
┌─────────────────────────────────────────────────────────┐
│                     完整处理链路                          │ 批量模式 │ 实时模式
├─────────────────────────────────────────────────────────┤
│ 1. 音频录制 (recorder)                                   │    ✅     │    ✅
│ 2. STT 转写 (stt_engine)                                │    ✅     │    ✅
│ 3. 繁简转换 (opencc)                                     │    ✅     │    ✅
│ 4. 🔥 热词替换 (hotword.py) [新增]                       │    ✅     │    ✅
│ 5. 命令匹配 (command.py)                                 │    ✅     │    ✅
│ 6. 🤖 LLM 后处理 (llm_postprocessor.py) [新增]          │    ✅     │    ❌*
│ 7. 文字注入 (injector)                                   │    ✅     │    ✅
└─────────────────────────────────────────────────────────┘
* 实时模式 LLM 后处理为可选，推荐默认关闭
```

## 五、实施建议

### 5.1 优先级判断

| 功能 | 开发量 | 用户价值 | 建议 |
|------|--------|---------|------|
| **热词系统** | 3-5 天 | ⭐⭐⭐⭐⭐ | **优先实现** |
| **LLM 后处理** | 5-7 天 | ⭐⭐⭐⭐ | 第二优先 |

**理由**：
- 热词系统开发量小、见效快、用户刚需，且对现有架构零侵入
- LLM 后处理依赖外部 API/模型，增加用户配置复杂度，但带来的体验提升是质的飞跃
- 两个功能在处理链路上是串行的，先做热词再做 LLM，LLM 可以在热词替换之后处理

### 5.2 热词系统详细设计

```
core/hotword.py
├── HotwordEntry(name, replacement, weight, category)
├── HotwordEngine
│   ├── load(file_path)          # 从文件加载热词表
│   ├── add(word, replacement)   # 运行时添加临时热词
│   ├── remove(word)             # 移除热词
│   ├── process(text) → str      # 替换处理
│   └── _build_trie()            # 构建替换 trie（性能优化）
└── HotwordConfig
    ├── enabled: bool
    ├── file: str = "hotwords.txt"
    ├── case_sensitive: bool = False
    └── mode: str = "replace"    # replace | append | both
```

**热词文件格式** (`hotwords.txt`)：
```
# 语音输入工具热词表
# 格式：识别文本 → 替换文本（可省略 = 相同）
# 分类：[通用] [工作] [技术]

[通用]
刘洋 → 刘洋
鹤壁 → 鹤壁

[技术]
CUDA → CUDA
Kubernetes → Kubernetes
React → React
Vue.js → Vue.js

[工作]
飞书 → 飞书
字节跳动 → 字节跳动
```

**替换策略**：
1. **精确匹配**：全文中出现的热词直接替换（最高优先级）
2. **拼音匹配**：可选，对中文热词进行拼音相似度匹配（复杂，v2 再做）
3. **FunASR 原生热词**：FunASR 引擎推理时传入 `hotword` 参数（模型级增强）

### 5.3 LLM 后处理详细设计

```
core/llm_postprocessor.py
├── LLMConfig
│   ├── enabled: bool
│   ├── provider: str             # openai | ollama | custom
│   ├── api_base: str             # API 端点
│   ├── api_key: str
│   ├── model: str                # 模型名
│   ├── timeout: float = 10.0     # 超时秒数
│   ├── mode: str = "polish"      # polish | translate_en | custom
│   ├── system_prompt: str        # 自定义 prompt
│   └── stream_mode: bool = False # 流式处理（实时模式预留）
├── LLMPromptLibrary
│   ├── get_preset(name) → str    # 获取预设 prompt
│   └── presets: dict             # 预设库
└── LLMPostprocessor
    ├── __init__(config)
    ├── process(text, callback)    # 异步处理
    ├── process_sync(text) → str   # 同步处理（实时模式不用）
    ├── _call_api(text) → str      # 调用 LLM API
    └── _timeout_fallback(text)    # 超时回退（返回原文）
```

**预设 prompt 模板**：

```
1. polish（润色模式）
   "将以下口语化的语音识别文本整理为流畅的书面语。
    保持原意不变，修正明显的识别错误，添加适当的标点符号。
    不要添加原文中没有的内容。"

2. meeting（会议纪要）
   "将以下会议记录整理为结构化的会议纪要。
    分段归纳要点，标注关键决策项。"

3. translate_en（中译英）
   "将以下中文文本翻译为英文。
    保持专业术语准确，自然流畅。"

4. custom（用户自定义）
   system_prompt 字段由用户自己写
```

**超时策略**（关键设计）：
- LLM 调用可能失败或超时（网络问题、模型卡住）
- 超时时 **自动降级为原文直接注入**，不阻塞用户
- 配置 `timeout: 5.0`，超 5 秒放弃后处理

### 5.4 依赖影响

| 新增依赖 | 用途 | 是否必需 |
|---------|------|---------|
| `httpx` 或 `requests` | LLM API 调用 | 仅 LLM 后处理需要 |
| `openai` (可选) | OpenAI 兼容 API 客户端 | 推荐，统一接口 |
| `pygtrie` 或 `marisa-trie` | 热词替换 trie | 可选，小词表用 dict 即可 |

**热词系统**：无额外依赖（纯 Python 实现）
**LLM 后处理**：`httpx` 一个新依赖（比 requests 更现代，支持 async）

## 六、风险评估

### 6.1 热词系统风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 误替换（把正常词换成错的） | 中 | 中 | 最小长度保护（>=2字符）+ 置信度阈值 |
| 热词表过大影响性能 | 低 | 低 | 热词上限 500 条，trie 替换 O(n) |
| 与 command.py 命令冲突 | 低 | 低 | 热词替换在命令匹配之前，不影响命令 |
| FunASR 原生热词 API 变更 | 低 | 低 | 作为可选增强，失败回退到文本替换 |

### 6.2 LLM 后处理风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| LLM 调用延迟 5-15 秒 | 高 | 高 | 仅批量模式开启 + 超时降级 + 进度提示 |
| API Key 泄露 | 中 | 高 | 配置文件本地存储，不上传云端 |
| LLM "幻觉"（添加不存在的内容） | 中 | 中 | prompt 明确约束"不添加原文没有的内容" |
| 本地 LLM 质量差 | 中 | 中 | prompt 适配本地模型 + 推荐云端 API |
| 网络不通时完全不可用 | 中 | 中 | 离线模式自动跳过后处理 |
| 实时模式体验差 | 高 | 高 | 实时模式默认关闭后处理 |

## 七、总结

### 热词系统 — 强烈推荐立即实施

**一句话**：开发量小（3-5天）、零架构侵入、用户刚需、竞品标配。

**实施路径**：
1. `core/hotword.py` — 文本替换引擎（Day 1-2）
2. `config.py` + `config.yaml` — 配置支持（Day 2）
3. `engine.py` — 集成到处理链路（Day 3）
4. FunASR 原生热词参数集成（Day 3-4）
5. Web UI 热词管理页面（Day 4-5）
6. 测试 + 文档（Day 5）

### LLM 后处理 — 推荐第二优先

**一句话**：体验质的飞跃，但引入外部依赖和延迟，需要谨慎设计降级策略。

**实施路径**：
1. `core/llm_postprocessor.py` — LLM 调用引擎（Day 1-3）
2. 预设 prompt 模板库（Day 3）
3. `engine.py` — 异步集成（Day 3-4）
4. Web UI 配置页面（Day 4-5）
5. 超时降级 + 错误处理完善（Day 5-6）
6. 测试 + 文档（Day 6-7）

### 组合效果

两个功能组合后，处理链路变为：
> 语音 → STT 原始文本 → **热词修正** → **LLM 润色** → 高质量文稿

这将是开源语音输入工具中 **最完善的文本处理管线**，远超任何单一竞品。
